# ADR 0002: 生物行为独立实现

## 状态

已接受

## 背景

双模式架构确定后，需要决定生物（Creature）的行为实现方式。
游戏模式和动画模式对生物的行为需求差异显著：

| 维度 | 游戏模式 | 动画模式 |
|------|---------|---------|
| 数量 | 多生物同时存在 | 单生物循环 |
| 移动 | 快速、随机、持续 | 自然、有停顿、有路径 |
| 生命周期 | 离开屏幕即消失 | 完整的进入→移动→停顿→退出状态机 |
| 交互 | 支持被捕捉 | 无交互 |
| 音效 | 捕捉音效 | 爬行/停顿音效 |

## 决策

为两种模式分别实现独立的生物类：

- **Creature** - 游戏模式生物，专注于快速移动和捕捉反馈
- **AnimationCreature** - 动画模式生物，拥有完整的状态机（entering → moving → pausing → exiting）

## 考虑过的替代方案

### 替代方案1: 单一Creature类，通过mode参数切换行为
在一个类中通过 `mode` 参数和条件判断来区分两种行为。

**拒绝原因**：
- 条件分支过多，代码可读性差
- 两种模式的行为逻辑会互相耦合
- 动画模式的状态机复杂度不适合用条件判断表达

### 替代方案2: 继承基类
创建 `BaseCreature` 抽象基类，`GameCreature` 和 `AnimationCreature` 继承。

**拒绝原因**：
- JavaScript 的类继承在小型项目中增加不必要的复杂度
- 两种生物的渲染逻辑几乎相同，继承收益有限
- 当前项目规模下，独立类更直观

## 后果

### 正面
- 每种生物类的职责单一，代码清晰
- 可以独立优化各自的行为逻辑
- 渲染逻辑可以共享（通过复制或后续提取工具函数）

### 负面
- 渲染代码存在重复（draw 方法相似）
- 修改通用渲染逻辑需要修改两处

## 缓解措施

未来如果渲染逻辑需要频繁修改，可以提取 `CreatureRenderer` 工具对象，将共享的渲染逻辑集中管理。
